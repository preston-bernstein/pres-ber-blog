# Plan: 2026 Image Pipeline (WebP/srcset/LQIP + Mermaid)

## Approach
Both gaps close the same way: add a small site-level override on top of a Blowfish theme file that already does 90% of the work, instead of writing new rendering logic from scratch. For images, the site-level `render-image.html` copies Blowfish's existing figure/caption/SVG/remote logic verbatim and adds two things on top: WebP format conversion and a base64 blur-up placeholder (LQIP, "low-quality image placeholder" — a tiny, heavily compressed preview shown while the real image loads). For Mermaid diagrams, a new codeblock render hook turns a fenced ` ```mermaid ` block into the exact same `<pre class="not-prose mermaid">` markup Blowfish's own `{{< mermaid >}}` shortcode already produces, so the already-vendored `mermaid.min.js` and the theme's existing dark/light re-render logic (`appearance.js`) pick it up with no new JavaScript. A third small file closes the one real gap in that reuse: Blowfish's per-page Mermaid JS loader only checks for the shortcode, not the fenced block, so a new `extend-head-uncached.html` partial adds that second check without touching the vendored theme.

## Architecture
Two independent pipelines, both driven by Hugo's render-hook mechanism (Hugo auto-discovers a template at a specific path and calls it instead of its default renderer, no explicit wiring needed per post).

**Image pipeline** — one Markdown image reference, one hook, three branches:

```
Markdown  ![alt](path "caption")
        |
        v
site/layouts/_default/_markup/render-image.html   (NEW override, wins over theme's copy)
        |
        +-- remote (http/https) or missing resource --> plain <img>, unchanged
        +-- local SVG resource --------------------------> plain <img>, unchanged, no WebP/LQIP
        +-- local raster resource (png/jpg/etc) ---------> figure with:
                - src/srcset resized to WebP at 800w/1280w (capped by original width)
                - inline base64 WebP LQIP as a CSS background, cleared on image load
                - data-zoom-src, loading="lazy", figcaption -- all unchanged from today
```

**Mermaid pipeline** — two Markdown entry points converge on one JS bundle, gated once per page:

```
Markdown  {{< mermaid >}}...{{< /mermaid >}}     Markdown  ```mermaid ... ```
        |  (existing shortcode, untouched)                |  (NEW render hook)
        v                                                  v
themes/blowfish/layouts/shortcodes/mermaid.html   site/layouts/_default/_markup/
        |                                          render-codeblock-mermaid.html  (NEW)
        v                                                  v
        +---------------> <pre class="not-prose mermaid">...</pre> <---------------+
                                          |
                                          v
        head.html  -->  vendor.html (unchanged: loads JS if .Page.HasShortcode "mermaid")
                    -->  extend-head-uncached.html  (NEW: loads JS if a ```mermaid
                         fenced block is present AND the shortcode check above
                         did NOT already trigger a load -- avoids loading the
                         bundle twice on a page that uses both)
                                          |
                                          v
                    mermaid.min.js + mermaid.js bundle (already vendored, unchanged)
                                          |
                                          v
              appearance.js: mermaid.run() on page load and on dark/light toggle
              (already exists, unchanged -- this is what actually paints the SVG
              and re-paints it with dark-mode colors when the switcher is clicked)
```

The one hazard this diagram has to respect: `head.html` (and everything it calls, including the new `extend-head-uncached.html`) runs before `.Content` is rendered — confirmed by reading `themes/blowfish/layouts/_default/baseof.html`, which calls `partial "head.html" .` before `<body>`, while `.Content` only renders later inside `single.html`. A flag set by a render hook (which only fires *during* `.Content` rendering) would still be empty when `head.html` checks it. The fix, per requirement 11, is to check `.RawContent` — the raw, un-rendered Markdown source, which Hugo has already read from disk by the time `head.html` runs — for the literal ` ```mermaid ` marker, instead of a `.Page.Store` flag. This is empirically verified against the site's pinned Hugo 0.164.0 binary, not assumed: `.RawContent` is a real, populated `Page` method that correctly detects a fenced mermaid block, and `.Page.HasShortcode "mermaid"` correctly returns `false` on a page that uses only the fenced block — confirming the two detection mechanisms are independent, as this plan assumes.

## Data model
No data model changes. This is a static Hugo site with no database.

## API / interface contract
This project's "interface" is what a post author writes in Markdown and what site params exist — there is no HTTP API.

**Images — no new authoring syntax.** The existing Markdown image syntax is untouched:
```
![alt text](images/blog/<post-slug>/<file>.png "optional caption")
```
WebP conversion, srcset, and LQIP are automatic and invisible to the author. No new front-matter field is introduced or required.

**Mermaid — one new authoring syntax, additive.** A post can now use a fenced code block instead of (or alongside) the shortcode:
```` ```mermaid
flowchart TD
  A --> B
``` ````
The existing `{{< mermaid >}}...{{< /mermaid >}}` shortcode continues to work exactly as before (requirement 13) — this is a second entry point, not a replacement.

**Config — no new params.** The pipeline reuses the existing `Site.Params.disableImageOptimizationMD` boolean (defined in `themes/blowfish/config/_default/params.toml`, default `false`, not currently overridden in this site's own `config/_default/params.toml`) as the single global escape hatch: set it to `true` and every Markdown image falls back to the pre-2026 non-optimized path (original format, no LQIP, still responsive-resized). No new Hugo config param, Hugo Module, or `go.mod` entry is added anywhere. This is a semantic expansion of an existing flag: before this feature, `disableImageOptimizationMD` only meant "skip responsive resizing." Now it also silently governs the new LQIP feature. A second, LQIP-specific flag was considered and rejected as over-engineering for a two-feature switch on a personal blog — one flag, documented here, is enough.

**Error / edge cases:**
- Image resource not found on disk → `resources.Get`/`GetMatch` returns nil → falls into the existing "no resource" branch → renders the raw `$urlStr` as a plain `<img>`. Unchanged from today.
- `disableImageOptimizationMD = true` → every image site-wide uses the original-format, non-LQIP path. This is a site-wide switch, not a per-image opt-out.
- Malformed Mermaid syntax inside a fenced block → the render hook and JS-load gate can't validate diagram semantics at build time (Hugo has no Mermaid parser); the vendored `mermaid.min.js` renders its own inline error output in the browser at runtime, same as it already does for the shortcode today. No new error handling needed here.

## Integration points
- `layouts/_default/_markup/render-image.html` — **new site-level file** (does not exist at the site level today; only the theme copy exists). Overrides `themes/blowfish/layouts/_default/_markup/render-image.html` via Hugo's standard site-wins-over-theme lookup. Copies the existing `RenderImageCaption` template and the `RenderImageSimple` template verbatim (byte-for-byte behavior for SVG, remote, and disabled-optimization cases). Only `RenderImageResponsive` changes, and it fixes a bug, not just adds a feature: the theme's original code only converts to WebP inside a width-gated conditional (`{{ if gt $originalWidth 800 }}{{ $img800 = $imgObj.Resize "800x" }}{{ end }}`), and spec-challenge reproduced a real bug in that pattern with a 400x600 test image — because the image is narrower than 800px, the conditional never runs, `$img800` falls back to the raw, un-converted source image, and the rendered `srcset` stayed `.png` with zero WebP output anywhere. The fix decouples "convert to WebP" from "don't upscale past the source size": every breakpoint always calls `.Resize` with `webp q75`, and the target width is capped at the original image's width with `math.Min` instead of skipping the resize — `{{ $img800 := $imgObj.Resize (printf "%dx webp q75" (math.Min $originalWidth 800)) }}` and the same pattern at 1280. The same `math.Min` cap applies to the LQIP (low-quality image placeholder) resize, so a source image narrower than the LQIP target doesn't skip conversion or error. The LQIP is pinned at 24px wide, quality 40 — tested directly in a browser and confirmed to look like a blur, not a broken thumbnail — base64-encoded into a `data:image/webp;base64,...` URI and set as a CSS `background-image` on the `<img>` tag, cleared via a one-line inline `onload` handler once the real image paints. A CSS `background-image` doesn't scale to fill its box by default, so the `<img>` tag also needs `background-size: cover` (and, for off-center source images, `background-position: center`), added as an inline style or a utility class alongside the existing `my-0 rounded-md` classes — without it, the placeholder shows as a small tiled or corner-anchored swatch instead of a blurred fill. Hugo's `.Resize "Wx webp ..."` (a single dimension, not `WxH`) already preserves the source image's aspect ratio, so the placeholder is proportionally scaled, not a fixed square; combined with `background-size: cover`, this already handles portrait and panorama source images correctly, no extra code needed beyond the cap and the CSS above. `data-zoom-src`, `loading="lazy"`, `sizes`, and the `srcset` attribute name/format are unchanged. Add a one-line code comment at the top of this file naming the exact theme file and Blowfish version it was forked from, so a future Blowfish submodule bump can be diffed against it.
- `layouts/_default/_markup/render-codeblock-mermaid.html` — **new file**. Hugo's per-language codeblock render-hook convention: Hugo auto-invokes this specific filename for any fenced block tagged `mermaid`. Body is one line: `<pre class="not-prose mermaid">{{ .Inner | safeHTML }}</pre>` — deliberately identical to `themes/blowfish/layouts/shortcodes/mermaid.html`'s output, so both entry points produce markup that `mermaid.min.js`'s own `document.querySelectorAll('pre.mermaid')` (in `appearance.js`) treats identically. `safeHTML` is required so Mermaid syntax like `-->` isn't HTML-escaped.
- `layouts/partials/extend-head-uncached.html` — **new file**, at an extension point `themes/blowfish/layouts/partials/head.html` already checks for (`{{ if templates.Exists "partials/extend-head-uncached.html" }}{{ partial "extend-head-uncached.html" . }}{{ end }}`, confirmed present, currently unused at the site level). Re-evaluated per page (a plain `partial` call, not `partialCached` like the neighboring `extend-head.html`), which is required here since the load decision is page-specific. Replicates vendor.html's existing `resources.Get`/`Concat`/`Fingerprint` calls for `lib/mermaid/mermaid.min.js` + `js/mermaid.js` (these resolve correctly from a site-level file because Hugo's asset pipeline searches all mounted layers, theme included, the same way `vendor.html` itself already does). Gate condition: `(and (in .RawContent "` + "```mermaid" + `") (not (.Page.HasShortcode "mermaid")))` — the `.RawContent` check catches fenced-block usage per the ordering hazard above; the `not (.Page.HasShortcode "mermaid")` guard is required and not just cosmetic: without it, a page using both the shortcode and a fenced block would get the Mermaid bundle loaded twice (once by `vendor.html`'s existing shortcode check, once by this new partial), producing two `<script>` tags. `vendor.html` itself is not modified. The `.RawContent` substring match is a text heuristic, not a structural Markdown-AST check: it would false-positive on prose that merely quotes the literal ` ```mermaid ` marker as example text, and it won't catch unusual fence styles (tilde-fences, etc.) that no one at this site actually uses. This is an accepted limitation, not a bug to fix — building real AST-based detection isn't worth it for a solo-author blog that controls 100% of its own content. Add a one-line code comment in this file pointing back to `vendor.html`'s own Mermaid-loading block, so a future edit to one file prompts a check of the other — these two files independently replicate the same resource-loading calls and could otherwise silently diverge.
- `content/english/blog/native-hugo-image-pipeline-webp-lqip-and-mermaid.md` — **new post**. Front matter follows the convention of the most recent existing posts (checked against `what-a-364-dollar-claude-code-session-taught-me-about-agent-hygiene.md`): `title`, `meta_title`, `description`, `date`, `categories`, `authors: ["preston-bernstein"]`, `tags`, `draft: false`; no `image:` field, matching the majority (23 of 26) of existing posts that already omit it. Body includes one real Markdown image reference reusing the existing asset `assets/images/blog/secure-services-docker-compose-and-nordvpn/dockerComposeWithVPNDiagram.png` (referenced as `images/blog/secure-services-docker-compose-and-nordvpn/dockerComposeWithVPNDiagram.png`, the same relative-path convention the existing post at `content/english/blog/secure-services-docker-compose-and-nordvpn.md` already uses successfully) with specific, hand-written alt text and a caption — this exercises the WebP/srcset/LQIP path. Body also includes one real ` ```mermaid ` fenced block diagramming this feature's own render-hook / JS-load-gate flow (the flow shown in Architecture above) — this exercises the fenced-code-block path. The post text describes this fenced-block syntax in words rather than showing the literal ` ```mermaid ` marker as example text, since showing it would trip the `.RawContent` false-positive heuristic described above, in the very post meant to demonstrate the feature working. Body also includes a second, smaller diagram using the existing `{{< mermaid >}}` shortcode syntax, captioned as a demonstration that the old shortcode syntax still works alongside the new fenced block. A site-wide grep confirmed zero existing pages use the shortcode, zero use a fenced mermaid block, zero reference SVG images, and zero reference remote images — without this addition, there would be no existing page anywhere to regression-test the shortcode path (requirement 13) or to serve as a real "both entry points on one page" fixture for the double-load-prevention guard, this plan's top risk area. Using both entry points in the demo post covers this with real content instead of a synthetic test fixture, while staying within the "one new post" scope. No existing post file under `content/english/blog/` is modified.
- `tests/e2e/image-pipeline.spec.js` — **new spec**. Navigates to the new demo post and asserts: the rendered `<img>`/`<source>` `src`/`srcset` file extensions are `.webp`; the srcset carries 800w and 1280w candidates; a `data:image/webp;base64,` URI is present as the placeholder before load and is cleared after `naturalWidth > 0` (mirrors the `img.evaluate(...naturalWidth)` polling pattern already used in `tests/e2e/blog-post-content.spec.js`); the image is still wrapped in `<figure>` with a `<figcaption>`, still carries `data-zoom-src`, and is not excluded from mediumZoom (no `nozoom` class). Also asserts the SVG and remote-image branches still render unmodified, using an existing SVG/remote image reference elsewhere in the site if one exists, or a minimal temporary fixture otherwise.
- `tests/e2e/mermaid.spec.js` — **new spec**. Navigates to the new demo post and asserts the fenced-block diagram renders as an `<svg>` inside `pre.mermaid` (not raw text, not an unstyled Chroma code block); asserts the JS bundle `<script>` is present on this page. Reuses the click-`#appearance-switcher`-then-assert pattern from `tests/e2e/dark-mode.spec.js` to assert the diagram's rendered colors differ between light and dark mode (a page reload is not required — `appearance.js` already re-runs `mermaid.run()` synchronously on switcher click, confirmed by reading that file). A second test navigates to a page with neither the shortcode nor a fenced block and asserts the bundle `<script>` is absent. A third test navigates to an existing page still using only the `{{< mermaid >}}` shortcode and asserts it still renders and still loads the bundle, unchanged (regression coverage for requirement 13).
- `themes/blowfish/**` — **not modified anywhere**. It's a git submodule; every change above lives under site-level `layouts/`, `content/`, and `tests/`.
- `config/_default/params.toml` — **not modified**. `disableImageOptimizationMD = true` is exercised only as a temporary local build-time check during verification (per acceptance criterion 8), not committed as a permanent site setting.

## Technology choices
None. Every piece already exists in the repo or ships with Hugo Extended:
- Hugo's built-in image processing (`.Resize`, WebP encoding, `base64Encode`) — already the mechanism the theme-level `render-image.html` uses today; this plan only adds arguments to calls that already exist, no new library. WebP output from `.Resize "WxH webp qNN"` is empirically verified against the site's actual pinned Hugo 0.164.0 extended binary: the resized file has the correct WebP magic bytes and the correct `image/webp` MediaType, not just a renamed file.
- Blowfish's vendored `mermaid.min.js` and `mermaid.js` theme config — already wired and working via the shortcode path; this plan adds a second Markdown entry point to the same bundle, not a second bundle.
- AVIF was considered and explicitly deferred: it compresses better than WebP, but encodes slower and has a slightly smaller browser-support ceiling. Not worth the added complexity — a `<picture>` element with a second source format — at this site's scale. WebP-only, no AVIF fallback, is a deliberate, revisitable choice, not a silent default.

## Risk areas
- **Double-loading the Mermaid JS bundle.** `extend-head-uncached.html`'s gate must explicitly exclude pages where `vendor.html`'s own `.Page.HasShortcode "mermaid"` check already fires, or a page using both the shortcode and a fenced block gets two `<script>` tags for the same bundle. The plan specifies the `and (not (.Page.HasShortcode "mermaid"))` guard for exactly this reason — verify it's actually implemented, not just intended.
- **LQIP sizing is now a pinned number, not an open judgment call.** The placeholder is 24px wide at quality 40 — tested directly in a browser and confirmed to read as a blur, not a broken thumbnail. This was an open question in an earlier draft of this plan; see the render-image.html integration point above for the exact resize call.
- **The render hook's `.Inner` reaching the DOM unescaped — confirmed safe, not an open question.** The codeblock render-hook context (`.Inner`, `.Type`, `.Attributes`) is a different object shape than the shortcode's `.Inner`, but this was tested directly: `.Inner | safeHTML` reproduces the shortcode's output byte-for-byte, including literal unescaped `-->`. No further verification needed here.
- **The render-image.html override applies globally, retroactively, to all 25 existing posts' images — confirmed, not speculative.** Requirement 16 only forbids editing the existing posts' `.md` files; it says nothing about their images being re-processed by the new shared hook, and there's no Hugo mechanism to scope a render-hook override to one post. This was reproduced directly: installing the new hook with zero `.md` changes converted all 4 images in the existing `secure-services-docker-compose-and-nordvpn` post to WebP with LQIP backgrounds. This is accepted as a one-time, one-way format change and the intended effect (a site-wide performance win), not a bug this feature needs to prevent or version — but it does change these posts' image URLs (new fingerprinted filenames), which could affect external hotlinks or search-engine image-index entries pointing at the old URLs. Because there's no staging environment, verification must run a full site build — all content, not just the demo post — before merging, and specifically check that no existing post's image, including any incompatible or corrupt source file among the 25 posts, breaks the global WebP conversion. A broken image render would go straight to production.
- **CSS class purging (`hugo_stats.json`) is not a risk — verified.** The site's existing `[build.buildStats]` and `[[build.cachebusters]]` config in `hugo.toml` already handles new Tailwind classes introduced by a template change: `not-prose` already appears in the current `hugo_stats.json`, and `mermaid` will appear automatically the first time any page renders `pre.mermaid`, with no extra build step required.
- **Dark-mode Mermaid testing depends on a live JS re-render, not a static snapshot.** `mermaid.run()` only fires on `DOMContentLoaded` and on an explicit switcher click (confirmed in `appearance.js`) — a Playwright test that only sets `prefers-color-scheme` or a `dark` class without actually clicking `#appearance-switcher` won't exercise the real re-render path and could pass without proving anything.
