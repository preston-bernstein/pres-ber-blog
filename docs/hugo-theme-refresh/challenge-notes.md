## Changes made
- **Author front-matter migration flagged as the single highest-risk step.** Three independent agents (Implementation Realist, Data Model Critic, and the Design Devil's Advocate indirectly) converged on the same finding: the new `authors:` key name, its value shape, and whether Blowfish expects a flat author file or a page-bundle directory are all unverified guesses, and a wrong guess produces **no build error** — it silently breaks author attribution on all 25 live posts. Fixed by adding a mandatory research-and-record step before any rewrite runs, splitting the rewrite into a dry-run-then-apply pair, and adding a full manual diff-review gate after the script runs — none of which existed before.
- **Corrected two factual errors in the plan**, one real and one not: `config/_default/module.toml` actually has 24 active `[[imports]]`, not 16 as originally stated (verified directly against the file) — fixed everywhere it appeared. Separately, a challenger agent claimed `hugo.toml`'s `[markup.tableOfContents]` and `[[params.plugins]]` blocks don't exist — I verified directly (they're at lines 102 and 130) and that claim was a false positive caused by a truncated 100-line file dump, not a real spec defect. Rejected, no change made.
- **Added the visual/browser verification gate the CLI build alone can't provide.** The build succeeding proves templates parse — it proves nothing about scrollspy behavior, dark/light flash timing, Disqus rendering, GA/GTM firing, or WCAG contrast. Added explicit browser-driven checks for all of these as their own steps, plus a documented one-line rollback command (`git revert <sha> && git push`) for a live incident, since the prior rollback plan only said "coordinate with team" on a solo-owned site with no staging.
- **Named three silent-regression risks that had zero requirement or acceptance criterion covering them**: Disqus comments possibly disappearing from all 25 posts, the `meta_title` SEO field going unused, and Google Tag Manager silently no longer firing (all three share the same failure shape — no build error, a real live-site loss). Each now has an explicit requirement forcing a documented decision instead of an accidental drop.
- **Fixed a real data disagreement**: `data/social.json` and the author page's own `social:` list already contradict each other today (different Font Awesome class format, one URL has "www." and the other doesn't). The plan previously just deleted the "redundant" file; now it requires reconciling which value is correct first.
- **Corrected a file-count error used throughout all three documents**: `content/english/blog/` has 25 real posts, not 26 — "26" was conflating the post count with the file count (25 posts + 1 `_index.md` = 26 files). Fixed everywhere this appeared, including two acceptance criteria that were unverifiable as originally worded because they claimed all "26 posts" needed an image, when only 3 of 25 actually have one.
- **Split three oversized steps and fixed four dependency errors** in steps.md: the author-rewrite step now has a dry-run-then-apply split with a review gate; two steps that both modified the same file were serialized instead of marked parallel; the CI-workflow-update step now genuinely depends on the local build passing, not just on the theme being installed.

## Critiques rejected
- Switching the primary theme choice from Blowfish to Congo — the Design Devil's Advocate raised a fair point that the plan didn't argue Blowfish over Congo in its own text, but the underlying research (zen reading mode, sticky TOC, KaTeX/Mermaid, active 2026 maintenance) is sound and already scoped Congo as the fallback if a real blocker surfaces. Fixed by adding the argument explicitly to plan.md instead of switching themes.
- The Implementation Realist's claim that `hugo.toml` is missing a TOC config block and plugin-loader blocks — verified false directly against the file (see "Changes made" above). This was an artifact of a 100-line-truncated file dump used for challenger context, not a real defect in the plan.
- Building new cookie-consent banner infrastructure to pair with the GA/GTM tracking that survives the migration — a real compliance gap, but building a new consent UI is out of scope for a theme/UI-layer migration. Kept as a documented risk-area note instead of new build work.
- Adding CI-level Git tag/commit-hash verification machinery for the Blowfish submodule pin — the plan already pins to a specific commit SHA via a tagged release, which is itself immutable; adding a `git verify-tag` CI gate is more supply-chain-security tooling than a personal blog's threat model warrants.
- Auditing Hugo's `--templateMetrics` build-log output and GitHub Actions' existing secrets masking for exposure risk — neither is a new risk this migration introduces; GitHub Actions already masks `secrets.*` values, and template metrics don't carry FTP credentials or other secrets.

## Open questions requiring human input
- **Homepage identity**: keep the current bio-forward homepage (requires a Blowfish template override) or accept Blowfish's stock recent-posts-plus-bio template? This is now an explicit requirement (a real design decision), but the actual choice needs to be made during implementation — it's a genuine preference call, not something a build step can resolve on its own.
  - **Resolved**: stock Blowfish homepage. No `layouts/index.html` or home-layout override exists in this repo.
- **Comments**: keep Disqus (if Blowfish has a compatible partial) or accept comments disappearing from all 25 posts? Same status — now a required, documented decision rather than a silent drop, but the actual answer needs to be made during implementation once Blowfish's comments-partial support is confirmed.
  - **Resolved**: kept. `layouts/partials/comments.html` wires Hugo's internal Disqus template via Blowfish's documented comments extension point.
